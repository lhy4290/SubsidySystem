## 口說版（與 09 全場講稿第 4、5 頁相同）

> 我選需求階段。情境是上線前兩週，國土署要延長租金補貼受理日，另一個部會反對。
>
> **第一，產出。** 規則規格書寫明哪個部會決定、誰簽核，不接受口頭變更；需求追溯表讓規則一改就知道要測什麼。
>
> **第二，取捨。** 凍結期只接受參數變更。談不攏就以簽核為準，先照原規則上線，新規則放在 Feature Flag 後面。要多蒐集個資或多傳欄位的變更，延到下一版。
>
> **第三，出事。** 參數設錯由我負責：先切回旗標止血，再用稽核 log 的身分證雜湊找出受影響的人推播通知，三十分鐘內向上報告。事後改成雙人覆核，測試沒過不上線。

以下各節是投影片內容與追問備答，不需要逐字唸。

## 情境假設

> 上線前 2 週，國土署要求租金補貼受理日由每月 1–10 日延長到 1–15 日，另一個部會認為會排擠其他補助的尖峰容量，兩邊意見不一致；高層要求如期上線。

## 簡報第 1 頁：產出與取捨

### 一、這個階段必須產出什麼、為什麼

| 產出 | 為什麼必須有 |
|---|---|
| **補助規則規格書**：每條規則的參數值、生效日、決策部會、簽核人 | 跨部會意見不一致時，以書面簽核為準，不接受口頭變更；出事時查得到是誰、何時決定 |
| **需求追溯表**：規則 → 程式參數 → 測試案例 | 規則一改，立刻知道要改哪個參數、要重跑哪些測試 |
| **跨系統介面規格**：與戶政、主管部會、金融機構傳哪些欄位、怎麼加密 | 規則變更若要多傳欄位，會連動對方系統，必須在需求階段就確認 |
| **個資衝擊評估**：蒐集哪些資料、保存多久（對應題三資料保存表） | 新規則若要多蒐集個資，告知文字與保存方式都要跟著改 |

### 二、理想做法做不到時，如何避開風險、如何取捨

- **理想做法**：規則凍結後才開發，改了就完整重測。上線前 2 週改規則，做不到。
- **我的決策**：凍結期內只接受「參數層級」的變更，例如日期、年齡、時段。
  - **部會意見不一致**：以規則規格書上的決策部會簽核為準。簽核前先照原規則（1–10 日）上線，新規則放在 Feature Flag 後面，簽核後再開啟。
  - **規則集中成資料**：題三程式把受理日期集中在 `SubsidyType` 一處、寫成資料而不是 if-else，改規則只動一行。目前仍需重新部署；正式環境把這份資料移到設定檔，就能改參數、不必重新部署。
  - **Feature Flag（設計，未實作）**：新舊規則同時存在，依簽核結果切換；出問題一鍵切回舊規則。
  - **自動化測試**：每個日期、時段、年齡邊界都有測試（題三共 74 個），改參數後幾秒內就知道有沒有改壞。
- **取捨**：需要新欄位、新流程、或多傳個資給其他系統的變更，**一律延到下一版**。這類變更要重做個資評估與跨系統介面，2 週內做不完，硬做的風險高於延後。

## 簡報第 2 頁：出事後如何負責

### 三、上線後出問題，如何負責、補救、向上說明

> 假設：新規則簽核通過、旗標開啟，但參數誤設為 1–5 日（應為 1–15 日），6 日起的申請人被誤判為「不在受理期間」。

- **負責**：「凍結期接受參數變更」是我做的決策，所以由我負責。先止血，事後再檢討流程，不先追究是誰輸錯。
- **補救**
  1. **分鐘級止血**：切回旗標（設計上為執行期切換，不必重新部署），立即恢復舊規則 1–10 日，6–10 日的申請人可以申請；再修正參數為 1–15 日、覆核後重新開啟旗標。
  2. **找出受影響的人**：稽核 log 記錄了每次查詢的原因代碼、時間與身分證雜湊，可以撈出「出錯期間被判為不在受理期間」的人。
  3. **主動通知**
     - App 使用者：通知服務保存「身分證雜湊 ↔ App 推播 token」的對應（見題三資料保存表），用雜湊找到裝置推播。
     - Web 使用者與已登出、收不到推播的人：下次登入時以身分證雜湊比對受影響名單，顯示提示；同時發布公告。不需要為此多保存電話或 Email。
- **向上說明**
  - **30 分鐘內第一報**：影響人數、時段、已採取的措施。
  - **事後根因報告**：參數變更只有一人輸入、沒有覆核；改善措施是參數變更改為雙人覆核，並把自動化測試設為上線前的必要關卡。
  - 用 log 的數據說明，不推給提出變更的部會。

## 備案：上線維運（追問時使用）

情境：補助開跑當天流量暴增，異常與客訴同時發生。

| 小題 | 重點 |
|---|---|
| 一、產出 | 壓力測試報告與容量規劃；Runbook（每種異常的處理步驟與負責人）；監控告警門檻（錯誤率、排隊人數、回應時間） |
| 二、取捨 | 真實高峰流量無法完全重現，所以用虛擬等候室限流，超過容量的人先排隊，保住系統。跨系統呼叫（戶政、主管部會）設逾時與降級，對方變慢時不拖垮本系統 |
| 三、出事 | 先降級非必要功能（例：申請進度查詢改讀快取），保住送件功能；對外公告預估恢復時間；事後用 APM 與 log 數據做根因分析。log 中的身分證已遮罩，調查時看不到完整號碼 |

## 可能被追問的問題

| 問題 | 回答重點 |
|---|---|
| 為什麼不直接拒絕規則變更？ | 補助規則屬於政策決定，技術團隊的責任是讓變更安全落地；但會明確說出哪些變更在時程內做得到、哪些做不到 |
| Feature Flag 會不會讓程式變複雜？ | 只用在「規則版本」這一個切換點，上線穩定後移除舊版，不讓 flag 長期累積 |
| 參數化之後誰可以改參數？ | 變更走規則規格書的簽核流程，由指定人員輸入，變更紀錄保留；這次事件後再加上雙人覆核 |
| 跨部會一直談不攏怎麼辦？ | 以規則規格書上的決策部會與簽核人為準；未簽核前維持現行規則上線，並記錄待決事項 |
